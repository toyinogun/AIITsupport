## Summary
This change puts an allow list under every log line and exported span, moves the cause tokens into `internal/cause`, adds an hourly retention pass in the agent (idle close, then message purge), and adds a Zammad scheduler, `noord-retention`, that deletes the assistant's old closed and merged tickets. I found no blocker. I tried to get personal data past the handler, the exporter, the scan, and the scheduler condition, and the design held: redaction runs in a wrapping handler (stronger than the `ReplaceAttr` the spec describes), error text is gone from every runtime log path, and the Zammad condition fails safe on a missing time. The one major is a test gap on the only irreversible step: nothing durable proves that a reclosed ticket or a recently merged ticket is kept. The minors are small hardening items. I read the tests and the Go changes in full. I did not run the suite; you told me `go test -race` with `TEST_DATABASE_URL` and `make lint` pass.

## Major
### 🟠 The delete rule's two most dangerous cases have no durable test, `internal/seed/helpdesk/live_retention_test.go:58`
**Problem**: Spec 0010 lists two cases as "owed to `/test`": a ticket whose `close_at` is past the window but whose `last_close_at` is inside it (must stay), and a tagged ticket merged inside the window (must stay). The live test does not have them. The kept ticket `closedNew` gets `close_at` and `last_close_at` both set to `recent` (line 68), so a regression from `ticket.last_close_at` to `ticket.close_at` in `retention.rb` would still pass. There is also no merged ticket inside the window. Only the one off probe in `verify.md` covers them, and the scope file already ticks "Test it".
**Why it matters**: Journal 0035 exists because this exact mistake (reading `close_at`) would delete a reopened and reclosed ticket at the next full hour, and Zammad deletion cannot be undone. This is the branching logic that decides what gets destroyed, and it is covered by a probe that nobody will rerun.
**Suggested fix**: In the Rails setup block, add one more tagged ticket that is closed, then set `close_at` old and `last_close_at` recent, and one tagged ticket merged and then given a recent `updated_at`. Assert both are still there after the forced run. Both are two or three lines in the existing script. Then the spec's "owed" bullet can be struck.

## Minor
### 🟡 `main` still prints raw error text to stderr, outside the handler, `cmd/agent/main.go:39`
**Problem**: Both mains do `fmt.Fprintf(os.Stderr, "%s: %v\n", service, err)`. At runtime, `run()` can return an error from the Slack socket (`fmt.Errorf("slack socket mode: %w", err)` in `internal/slack/listener.go`), from `server.Run`, and from the shutdown join. Those texts come from slack-go, the HTTP stack, and pgx, and are printed as is. The runbook admits this (`docs/runbooks/data-retention.md`, "A binary's exit line"). `cmd/toolserver/main.go:35` is the same.
**Why it matters**: AC-3 and the spec's key invariant say no runtime error text reaches output. Today I could not find a path where these errors quote a name or message (Slack returns codes, pgx startup errors name hosts and users, not rows), so the risk is low. But it is the one place the rule "never print error text" is not enforced in code, and a future error that wraps a row detail would print it.
**Suggested fix**: Keep the full text only for errors returned before the logger and serve loops start (config and connect errors, which name settings and never values). For errors that come out of `g.Wait()`, print `service: ` plus `cause.Of(err)`. Or note the exception in the spec's Consequences, not only in the runbook.

### 🟡 `WithGroup` names and `attribute.Key` method calls are blind spots in the scan, `internal/logging/scan_test.go:33`
**Problem**: `slogArgsFrom` has no `WithGroup`, so `logger.WithGroup(name)` with a dynamic name passes the scan. The handler redacts every value after it, but the group name itself is printed as a JSON key. Separately, `case path == attributePath && recv == nil` (line 163) skips method calls such as `key.String(v)` on an `attribute.Key` variable or a semconv key, because they have a receiver. AC-2 names the `attribute.Key(...)` methods. A key built with `var k attribute.Key = "email"` has no conversion call for the scan to see either.
**Why it matters**: Only the key name can leak here (values are still replaced at run time), so the harm is small. But the scan is the stated second layer and it has two holes that are easy to close.
**Suggested fix**: Add `WithGroup` to the scan and report any use in runtime code (the handler already makes it useless). For `attribute.Key` methods, check the key where the `Key` value is built, or report any `attribute.Key` variable that is not a constant string literal.

### 🟡 The purge is one unbatched update with a 5 minute cap, so a big backlog can never finish, `internal/agent/retention.go:15`
**Problem**: `PurgeMessageContentBefore` updates every matching message in one statement, and the step now has a hard 5 minute timeout. If the first pass meets a backlog that takes longer than that (for example after the agent was off for months, or after a long dev history), the statement is cancelled and rolled back, logged as `retention_purge_failed` with `deadline`, and retried an hour later with the same backlog. It never makes progress. The query also scans every closed conversation ever, every hour.
**Why it matters**: The spec accepted "unbatched, fine at this volume", and that is true today. The review time timeout turned a slow query into a stuck one, and the failure looks like a transient warning.
**Suggested fix**: Either add a row limit to the purge (a `LIMIT` over a subselect, repeated until it returns fewer rows than the limit, inside one pass), or raise the cap and note the volume assumption in the runbook. At minimum, tell the reader in the runbook's check section that a repeating `retention_purge_failed` with `deadline` means the backlog is too big for one pass.

### 🟡 Lowering the window deletes real tickets at the next full hour with only a printed count as a guard, `cmd/seed/helpdesk.go:59`
**Problem**: The range check allows `TICKET_RETENTION_DAYS=1`. A typo (`3` for `30`, or a stale shell variable) followed by `make helpdesk-seed` arms the scheduler with the new window, prints `tickets_matching_now`, and returns. Nothing waits for you. The first delete runs at minute 0, up to 2000 tickets per hour, and Zammad deletion is permanent.
**Why it matters**: The spec calls ticket deletion "the one irreversible step" and answers it with a log line. On a dev stack that is acceptable, but the same command will run in the cluster (#17).
**Suggested fix**: When the new window is shorter than the stored one and `tickets_matching_now` is above zero, make the seed stop and ask for an explicit flag (for example `--allow-shorter-window`), or at least log that line at warn. The Rails step already knows the old value from the stored condition.

### 🟡 The first retention pass can race the restart sweep and swallow an old interrupted conversation, `cmd/agent/main.go:83`
**Problem**: `retention.Run` starts at once in the errgroup, while `runSlack` runs `a.Sweep(ctx)` before the socket opens. A conversation that was interrupted more than N days ago (agent down for a month) is either escalated by the sweep or idle closed as `resolved` by the retention pass, depending on which statement reaches Postgres first. In the second case the user's request never reaches IT.
**Why it matters**: It is rare, and a request that old is probably stale. But the outcome is random, and the sweep's claim then fails with `ErrNotOpen`.
**Suggested fix**: Decide the rule and make it deterministic. Either start the retention loop after the sweep returns, or make the sweep skip conversations older than the window and say so in the spec.

## Strengths
- Redaction is deny by default in the wrapping handler: it resolves `LogValuer`s, treats a group as one redacted value, never lets `WithGroup` or `With` bypass it, and drops `error` from the key list entirely. The tests cover the awkward inputs (an `error`, a struct, an email, a two word name, a 129 byte id, a `msg` key, a grouped key).
- The exporter wrapper embeds the span and overrides only what carries text (attributes, events, status description, links, scope, and the deprecated `InstrumentationLibrary`), builds new slices, and a test proves the original span is unchanged. Resource attributes are limited to `service.name`, so no host data leaks.
- `internal/cause` is a clean leaf with a token shape check for adapter causes, and every runtime `err.Error()` log in the Slack listener became a `cause`. The HTTP server bridge drops the text of panics and TLS errors, and a test panics a handler on purpose.
- The retention SQL is correct on the points I traced: the idle close and the purge share the `status` and `closed_at` invariants, `closed_at = updated_at` keeps the CHECK constraint, `UpsertConversation` bumps `updated_at` before the status is read so a live message cannot be idle closed, `SetConversationStatus` still guards `status = 'open'`, and the DB test proves `noord_agent` still cannot DELETE.
- The Zammad rule fails safe: tag first, then `closed` with `last_close_at` or `merged` with `updated_at`, a null time never matches, the days value is parsed as an integer in 1 to 365 before use, and the env value never reaches a shell. The seed output prints how many tickets match before the first run, and the marker leaves `retention.rb` out so edits do not force a reset.
- The retention loop is simple and safe on shutdown: one goroutine, a ticker that stops, a per step timeout, no log line when the context ended, and `Run` returns nil.

## Test coverage
Good for the logging and retention work: handler cases, the typed scan with a fixture that names each bad line, exporter and error handler tests, the cause tests in the Slack and server packages, config range tests for all three loaders, in memory and Postgres retention tests (closed 31 and 29 days, idle 31 days, active, a second pass at 0 rows, DELETE denied), and a canary per binary that hunts every seed name, username, email, Slack id, department, and scripted text in log and span string values. Gaps: the two live Zammad cases in the Major above, no test for `WithGroup` names or `attribute.Key` method calls in the scan, and no test that covers a backlog larger than the step timeout. I did not check whether Zammad's `History` rows for a deleted ticket are removed; the spec says "the whole history" goes, and the live test only checks the ticket API returns 404.
