## Summary
The change replaces the holding reply with the real agent loop: a Slack gate and code owned `user_lookup` before the model runs, a bounded hand written tool loop, a failure path that leaves IT a ticket, per thread FIFO workers, a restart sweep, pricing, and trace propagation. The design is faithful to spec 0008 and the code is tidy, well factored, and well tested (`go test -race` passes for agent, slack, llm, eval, config, cmd/agent; agent package coverage 80.5%). I found no blocker. The headline issue is that the cause of every model, tool server, Slack, and post failure is dropped without a log line or span event, which will make the first real outage (bad API key, 400 from a malformed request, missing Slack scope) opaque. The rest are minors around the sweep and the tool definition cache.

## Major
### 🟠 Failure causes are discarded: no log, no span event, `identity.go:83-91`, `loop.go:104-111`, `identity.go:38-42`, `agent.go:263-269`
**Problem**: `callTool` drops the `error` from `Tools.Call` and returns the fixed unknown text. `callModel` drops the `error` from `Model.New` (the span only gets the static status "model call failed") and maps every error, including a 400/401/403 that is not an outage, to `model_unavailable` with the note "the model API could not be reached". `identify` drops the `users.info` error and posts `slack_try_again` with no log line (only `outcome=slack_retry` in `agent_turn_done`). `post` logs `agent_post_failed` with the event id and kind but not why. `toolDefs.get` failures are likewise collapsed to `toolserver_unavailable`.
**Why it matters**: A wrong or revoked `ANTHROPIC_API_KEY`, an invalid request (for example a tool schema Anthropic rejects), a missing `users:read.email` scope, or a rate limit all look identical in the logs: `agent_escalated reason=model_unavailable` or `slack_retry` and nothing else. The user rule says never silently swallow errors, and the tool server already has the pattern to copy (`cause()` in `internal/tools/refusal.go` gives a fixed token such as `zammad_<status>`, `ldap_<code>`, `deadline`, `network`). `TestLogsAndSpansHoldNoPersonalData` even feeds a model error containing "ZEBRA" to prove it is not logged, so the omission is deliberate, but AC-17 only forbids personal data, not a fixed cause token.
**Suggested fix**: Classify each error into a small fixed token set (HTTP status class for the SDK's `*anthropic.Error`, `deadline`, `canceled`, `network`, Slack API error code string for `users.info`, MCP transport vs JSON-RPC) and add it as a `cause` attribute on the existing `agent_escalated` / `agent_post_failed` lines and on the `llm.call` / `agent.turn` spans. Never log `err.Error()` (it can quote content). Add a hygiene test case that the cause token appears and the error text does not.

## Minor
### 🟡 Sweep never stores the escalation ticket id (runtime observation a, b), `sweep.go:42-57`
**Problem**: `recoverInterrupted` claims the conversation first with `SetStatus(escalated)`, then `ensureTicket` creates the ticket and returns `ticketOutcome.created`, which is thrown away. `SetConversationStatus` only updates `status = 'open'` rows, so the id can no longer be stored. The turn path does it right (`failure.go:26` passes `TicketID: tk.created` in the same escalation write). That is why live conversation 6 ended `escalated` with `zammad_ticket_id` NULL.
**Judgement on the spec**: AC-14 says "ensures a ticket as in AC-10" and AC-10 does not itself say to store the id, so this is not a literal AC violation. It is an inconsistency between the two failure paths, and it is not the "durable state in Postgres" rule (nothing is held in memory; the ticket exists in Zammad and the `ticket_update` audit row carries the id). Impact is real but bounded: follow up #11 posts escalations to IT "with the thread link and ticket" from exactly these conversation rows, so every restart escalation will lack its ticket. It is not a double ticket risk, because `ticket_create` also refuses `has_ticket` from the audit history (`internal/tools/tickets.go:25`).
**Why the claim first order (b) matters**: it is a deliberate guard so a new message in the thread finds `closed_thread` and the sweep and a turn never act together, which is sound, and AC-14's "either way it sets escalated" does not fix an order. The cost is (a) above, plus a crash between the claim and the post leaves the user with silence and IT with nothing, and the conversation is terminal so no later sweep retries it.
**Suggested fix**: Keep the claim but let the claim write be skipped for the ticket: either register the thread as busy in memory during the sweep (so `Submit` queues behind it) and make the final `SetStatus(escalated, TicketID)` the only write, or add a narrow query that can fill `zammad_ticket_id` on a row the sweep just escalated. Add a `TestSweep` assertion on the stored ticket id (it currently checks only status and posts).

### 🟡 Sweep treats a transient failure as "no match" and makes it permanent, `sweep.go:54-62`, `sweep.go:68-87`
**Problem**: `reidentify` returns false for a `users.info` error, a tool server that is not up yet, or `unavailable`, exactly like a real non match. The startup sweep runs while the tool server may be restarting in the same deploy, and the conversation is already `escalated`, so the user gets `escalated_no_ticket` ("I couldn't open a ticket either") and IT gets nothing, with no retry in the second sweep.
**Why it matters**: A rolling deploy of both services is the most likely time the sweep has work, and also the time the tool server is least likely to answer.
**Suggested fix**: Distinguish "answered, no match" from "could not ask". For the latter leave the conversation `open` (do not claim) so the second sweep, 95 seconds later, tries again; only escalate with `escalated_no_ticket` on a definite refusal or on the second pass. The spec text for AC-14 would need a one line note.

### 🟡 Shared tools/list fetch is bound to the first caller's context, `tooldefs.go:33-52`
**Problem**: `singleflight.DoChan` runs `fetchTools` with the first caller's `ctx`. If that turn's deadline expires or it is cancelled mid fetch, the shared fetch fails with a context error and every concurrent waiter, whose own deadlines are fine, gets the same error and fails with `toolserver_unavailable`. The comment says each waiter honours its own deadline, which is true for waiting but not for the fetch.
**Why it matters**: Only on the first fetch (or after a failed fetch) with several turns arriving together, and only if the first one is slow, so rare, but the outcome is a wrong escalation for innocent users.
**Suggested fix**: Run the fetch on a context derived from the agent's work context with its own `AGENT_TOOL_TIMEOUT` (like `callTool` does) and let waiters select on their own `ctx`.

### 🟡 Any Go error from `Tools.Call` is reported as "outcome unknown, tool server unreachable", `identity.go:83-91`, `mcpclient/client.go:104-107`
**Problem**: `mcpclient.Call` returns an error for JSON-RPC protocol errors as well as transport errors (for example the SDK answering an unknown tool name, which `internal/tools/AGENTS.md` notes happens before the dispatcher). The model can call a tool name that is not in the list. That is treated as `toolserver_unavailable` with `unknown: ... may or may not have run`, an escalation, and a note saying the server could not be reached.
**Why it matters**: Low frequency, but it escalates a conversation that a plain error tool result would let the model recover from, and the note misleads IT.
**Suggested fix**: Have `mcpclient` return a typed protocol error (or an `IsError` result with a code) for JSON-RPC errors that prove the call did not run, and keep "unknown outcome" for transport and timeout errors only.

### 🟡 `ErrNotOpen` from `AppendToolResult` is reported as a database outage, `loop.go:189-193`
**Problem**: If the sweep (or anything else) escalated the conversation while a tool call was in flight, the store keeps the result and returns `ErrNotOpen`, but the turn maps every store error to `store_unavailable` and the user and IT see "the assistant's database could not be reached".
**Why it matters**: Wrong reason in the log, the ticket note, and the metric. The window is tiny because the sweep skips threads with a worker, except for the gap between its `running()` check and its claim.
**Suggested fix**: Map `ErrNotOpen` to its own outcome (stop the turn, post nothing more or a fixed text) and close the check then claim gap by registering the thread while the sweep handles it.

## Nits
- ⚪ `loop.go:90`, the requester block is built from the turn's first `user_lookup`, so after `account_unlock` succeeds in the same turn the next model call still sees "Account locked: yes". It matches the spec ("rebuilt every turn") and the live run was fine, but a model that distrusts the tool result could unlock twice; the prompt could say the tool results are newer than the block.
- ⚪ `turn.go:144-146`, `loop.go:107`, a context cancelled by the shutdown grace expiring (not the turn deadline) is labelled `message_timeout`. Harmless, but the note says "time limit for one message".
- ⚪ `agent.go:134-137`, `agent.go:142`, channel mention redirects and `busy` posts are unbounded goroutines outside the concurrency cap. Slack dedup and rate limits make this theoretical.
- ⚪ `internal/slack/AGENTS.md:5,10,12` and the root `AGENTS.md` context file list still describe `HoldingReply`, which this change removes; `/sync` is queued in the spec's build plan but the docs are stale until then.
- ⚪ `eval/pricing.yaml`, the prices cannot be checked from the repo; the comment says "copied from Anthropic's published pricing" with a 2026-10-06 date. Worth a one time check against the `claude-api` pricing reference, since `cost_microusd` is a recorded fact.

## Strengths
- The identity design holds up under scrutiny: `Requester` is built only from the event, `users.info`, and the conversation row; `user_lookup` is not offered to the model; the second `tool_use` block is answered, not run; `TestModelCannotChangeTheRequester` and the widened depguard plus transitive boundary test back it.
- Context discipline is careful and consistent: a turn context derived from a work context that only the shutdown grace cancels, detached contexts for started tool calls, result stores, status writes, usage rows, escalation tickets, and posts, and the tool result plus ticket id / `resolved` committed in one transaction (`AppendToolResult`), with a real Postgres test.
- Worker, queue cap, semaphore, shutdown drain, and the order "listener stops, then agent drains" in `cmd/agent/main.go` are race free as far as I can trace (queue changes and worker deletion share one mutex; `wg.Go` is never called after `Wait` starts).
- The fakes in `agenttest` answer like the SQL (gapless seq, status guarded by `open`, context aware), so the unit tests exercise real semantics, and the spec's critical scenarios map to named tests one for one.
