## Summary
The change builds the tool server from spec 0007. It adds the audited dispatcher with its ordered checks, the registry of five tools with risk tiers, the kill switch, the group fence, the MCP server with a bearer check and a `_meta` identity check, the agent side MCP client, and `internal/ldap`, which the seeder now shares. I tried to break the security core and could not find a way past it. Identity comes only from `_meta`, no argument carries a target, account tools can only touch the matched requester, free text never reaches `audit_log`, and the agent deny lists are updated in both places. `go vet`, `golangci-lint` (0 issues), and `go test -race` on the touched packages all pass. What is left is edge case behavior around the call deadline, diagnosability, a few small test gaps, and style nits.

## Minor
### 🟡 A call whose deadline runs out before the handler loses its audit pair, `internal/tools/dispatcher.go:335`
**Problem**: `fail`, `refuse`, and the rate limit read all write through `Recorder` using the call context that carries `TOOL_CALL_TIMEOUT`. Only the outcome row uses `context.WithoutCancel`. The intent insert derives its timeout from the same context. If identity lookup (dial, bind, search, each up to `LDAP_TIMEOUT`) uses up the 15 second call budget, the context is already expired when `fail` runs. The intent insert then fails at once with `ErrAuditUnavailable`, nothing is written, and the model sees `failed` instead of `unavailable`. I found this by reading `insertIntent` in `internal/audit/audit.go`; no test covers it, because `TestCallTimeout` only hits the deadline inside the handler, where the outcome row is protected.
**Why it matters**: AC-3 and AC-19 say a call that fails still leaves one pair and says `directory unavailable`. In an outage with slow, not refused, connections this is exactly when the audit trail and the right message are wanted. No write happens in this path, so it is not an integrity problem.
**Suggested fix**: Run the refuse and fail writes, and the rate limit read, on `context.WithoutCancel(ctx)` with the recorder's own write timeout, as the outcome path already does. Add a test where the directory fake blocks until the call deadline during identity.

### 🟡 The real cause of a failure is never logged or stored, `internal/tools/dispatcher.go:335`, `internal/tools/refusal.go:132`
**Problem**: A failure keeps the wrapped error, but it is dropped. The audit `error` column holds only the fixed reason, and the log line holds only tool, tier, outcome, and trace id. The model sees `The action failed.` An operator who sees `action failed` (LDAP insufficient access, Zammad 403, a broken `ZAMMAD_DEFAULT_GROUP`) has nothing to go on.
**Why it matters**: The spec keeps personal data out of logs (AC-20), which is right, but it leaves no safe diagnostic either. This will cost real time in the first cluster deploy and in the eval work (#19).
**Suggested fix**: Decide on a safe diagnostic that carries no names, for example the LDAP result code or the Zammad HTTP status, and add it as one more static key (`cause`) on the `tool_call` line, or log a separate `tool_call_failed` line. Add it to AC-20 so the hygiene test covers it.

### 🟡 `audit_unavailable` is logged for a handler failure that did write an outcome, `internal/tools/dispatcher.go:294`, `internal/tools/tickets.go:23`
**Problem**: `ticketCreate` wraps a `ThreadHasOK` error with `failed(err)`. That error wraps `audit.ErrAuditUnavailable`, and `Recorder.Run` returns the handler error whole, so `errors.Is(err, audit.ErrAuditUnavailable)` in `run` is true. The dispatcher then takes the "intent could not be written" branch and logs `audit_unavailable`, although the intent and an `error` outcome were both written.
**Why it matters**: The model gets the right text either way, but the log line claims nothing was recorded. It will mislead someone reading logs during a database incident.
**Suggested fix**: Tell the two cases apart without `errors.Is` on the chain, for example by checking `errors.Is` only when `handlerErr == nil`, or by having the handler convert the history error into a plain `failed(nil)` before it returns.

### 🟡 `LDAP_URL` is not checked at startup, `internal/config/config.go:80`, `cmd/toolserver/main.go:46`
**Problem**: `LDAP_URL` is only required to be non empty. The dialer refuses anything that is not `ldaps://`, but only when a call dials. A tool server started with `ldap://...` passes startup and then fails every call as `action failed`, with the cause dropped (see above).
**Why it matters**: A configuration mistake becomes a runtime incident with no clue. AC-16 allows configuration only checks, and a scheme check is one.
**Suggested fix**: Parse `LDAP_URL` in `toolConfig` or `checkToolLayer` and refuse any scheme but `ldaps` with a named setting.

### 🟡 Test gaps on the identity edge and the LDAP client, `internal/tools/dispatcher.go:214`, `internal/ldap/client.go:77`
**Problem**: The `ErrTooManyMatches` to `ambiguous` branch in `identify` has no test. Nothing exercises the size limit mapping in `FindUsersByMail` either, since the fake directory is what the unit tests use and the live test only has two users sharing a mail. Unit coverage is 91% for `internal/tools` and 94% for `internal/mcpserver`, but only 45% for `internal/ldap` and 43% for `internal/mcpclient` without the gated live runs. `Under` and `CheckRelativeOU` are well covered; the `Client` and `Writer` methods rely on `TEST_SAMBA=1`.
**Why it matters**: The size limit branch is the fail closed path that stops a mail wildcard or flood from matching the wrong person. It is cheap to test and easy to break by a go-ldap upgrade (a partial result returned with the error).
**Suggested fix**: Add a dispatcher test with `dir.Err = ldap.ErrTooManyMatches` that expects `CodeAmbiguous`, and a live or stubbed `FindUsersByMail` test for the size limit error.

### 🟡 `Helpdesk.states` holds a mutex across a network call, `internal/tools/helpdesk.go:37`
**Problem**: The mutex is held while `TicketStates` waits on Zammad. A waiting caller cannot be cancelled by its own context, so a stalled Zammad can hold later `ticket_update` calls past their `TOOL_CALL_TIMEOUT` (by up to `ZAMMAD_TIMEOUT`).
**Why it matters**: It stretches the "call ends before the agent gives up" rule and queues calls behind one slow request on first use.
**Suggested fix**: Use `sync.Once` style loading with a result channel that waiters can select on with their context, or load the states without the lock and store them under it.

## Nits
- ⚪ `internal/mcpserver/meta.go:78`, `ticketID` re-marshals the decoded float, so `1e3` or `2.0` sent as the ticket id is accepted as 1000 or 2. The AC wants a JSON integer. Harmless (agent code sets it), but the "exact value" intent is not met for those forms.
- ⚪ `cmd/toolserver/main.go:113`, `toolLayer` returns bare errors from `NewRecorder`, `zammad.New`, `NewRegistry`, and `mcpserver.Handler`. The AGENTS.md rule is to wrap with context.
- ⚪ `internal/tools/fence.go:15`, `FloorDeniedGroups` is an exported mutable slice. The comment says no setting can remove a floor group, but any package could change it. Make it unexported with an accessor that returns a copy.
- ⚪ `internal/tools/dispatcher.go:139`, `dispatch` is about 70 lines, over the 50 line guideline, and `dispatcher.go:173` builds a map literal on every identity refusal. A small `identityRefusal(found)` helper would read better.
- ⚪ `internal/tools/dispatcher.go:79`, `beforeHandler` is a test hook living on the production struct. It is nil in production, but a test only constructor option would keep it out of the binary.
- ⚪ `internal/server/server.go`, the server now serves an authenticated endpoint but sets only `ReadHeaderTimeout`. A token holder can send a body slowly with no read deadline until the call timeout starts. Behind the NetworkPolicy this is low risk; consider `ReadTimeout` and `IdleTimeout`.
- ⚪ `internal/mcpclient/client.go:70`, `New` accepts an `http://` endpoint and sends the bearer token in clear text. Intended for in cluster traffic, but a one line doc comment saying so would help the next reader.
- ⚪ `docs/specs/0007-tool-server-risk-tiers/verify.md`, the `make check` line is still unchecked (it waits on committed sqlc output). It should be checked off or noted before the PR is opened.

## Strengths
- The "typed by what it may touch" design works. Only `AccountHandler` receives the directory writer, the kill switch and rate limit are derived from the handler type, and `TestDispatcherGatesEveryAccountHandler` proves it with a test tool. There is no flag to forget.
- Arguments are validated by our own validator before identity, and only allow listed non free text keys ever reach `audit_log`. This closes the exact gap the previous data model review raised about model controlled key names and error text.
- Fail closed choices are consistent: an unresolved denied group refuses every check, a kill switch read error pauses changes, more than 50 mail matches is `ambiguous`, and a blocked tool never reaches LDAP or Zammad.
- The transport is careful: SHA-256 digest compare in constant time, token check before the body cap, `_meta` formats matched exactly with no trimming, redirects refused in the client, and no retry of a call that may have written.
- Boundary hygiene: `internal/tools` and `internal/mcpserver` are on both agent deny lists and the lists are kept in sync by an existing test, `cmd/toolserver` has a test that it never links `internal/seed`, and the `internal/ldap` extraction left the seeder tests green.
- The spec's design questions (computed lock flag, chain matching rule on Samba, Zammad tag on create) were settled by live tests and recorded in the nested AGENTS.md files.

`go test -race` passes for `internal/tools`, `internal/mcpserver`, `internal/mcpclient`, `internal/ldap`, `internal/config`, and `cmd/...`; coverage is 91% (`tools`), 94% (`mcpserver`), 45% (`ldap`), and 43% (`mcpclient`) without the gated live suites. ## Follow up, 2026-10-18
All six minors are fixed. Each fix has a test, and the deadline, thread read, and helpdesk tests were checked to fail on the old code first. The nits are still open.

- **Deadline loses the audit pair**: fixed. Audit writes and reads outside the handler (refusals, `fail`, the rate limit count, `Defer`) now run on `context.WithoutCancel`, bounded by the recorder's own write timeout. A call whose checks used up the budget now stops before the handler with `directory unavailable` and a pair. The in memory store now fails a query whose context has ended, as Postgres does. Tests: `TestDeadlineDuringIdentityStillLeavesAPair`, `TestDeadlineAfterTheChecksStillLeavesAPair`.
- **No safe failure cause**: fixed. A failure now logs one `tool_call_failed` line with `tool`, `code`, `trace_id`, and `cause`, a fixed token such as `ldap_50`, `zammad_403`, `deadline`, `network`, or `audit`, never error text. Tests: `TestFailureCauseIsLogged` (also checks that no name, Slack id, argument, or directory or Zammad message leaks), `TestCause`. AC-20 in the spec and the logging line in `internal/tools/AGENTS.md` should mention this line; that is for `/architect` and `/sync`.
- **`ThreadHasOK` error logged as `audit_unavailable`**: fixed. `run` checks the handler error before `ErrAuditUnavailable`, and `fail` tracks whether its action ran instead of matching the error chain. Test: `TestThreadReadFailureIsRecordedNotUnavailable`.
- **`LDAP_URL` not checked at startup**: fixed. `checkToolLayer` refuses anything but an `ldaps://` URL with a host, naming the setting but not the value. Test: `TestLDAPURLMustBeLDAPS`.
- **Test gaps on the identity edge**: fixed. The search moved into `usersByMail`, which takes `goldap.Client`, so it is unit tested: escaping, the disabled filter, the size limit, and the size limit returning no users even with a partial result. Tests: `TestUsersByMailSearch`, `TestUsersByMailSizeLimitIsTooManyMatches`, `TestUsersByMailWrapsOtherErrors`, and `TestTooManyMatchesIsAmbiguous` for the dispatcher branch.
- **`Helpdesk.states` holds a mutex across a network call**: fixed. The lock now guards only the cached maps, so each caller is bounded by its own context. Callers that race on a cold cache each load once, and the first result is kept. Tests: `TestStatesWaitersHonorTheirDeadline`, `TestStatesAreCachedAfterTheFirstLoad`, `TestStatesRetryAfterAFailedLoad`.

`golangci-lint` reports 0 issues, and `go test -race` passes for every package under `internal/` and `cmd/`, including the Postgres tests.
