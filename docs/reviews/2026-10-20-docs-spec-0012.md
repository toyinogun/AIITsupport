## Summary
This change adds feature 14: a medium tier `mfa_clear` tool that only asks, an IT card in Slack, a tool server decision route that runs the clear once after a human click, and an agent side tick that expires, adopts, posts and settles every approval. The design holds up. The approval rules live in guarded SQL, the model has no route to an approval, the clear re checks the account, the kill switch and the Entra user right before the write, and an approval can run at most once. I ran `go build`, `go vet`, `make lint` (0 issues), `go tool sqlc diff` (no drift) and `go test -race` across the repo, including the Postgres backed tests against the local database, three times over the busiest packages: all green and stable. I found no blockers and no majors. The findings below are small correctness gaps, one unenforced invariant, and a few test and observability holes.

## Minor
### 🟡 "At most one pending approval per account" is checked, not enforced, `internal/tools/mfa_clear.go:64`
**Problem**: The precheck reads the pending approval, and `Defer` (`internal/tools/dispatcher.go:325`) inserts a new one later. Nothing in the database stops two requests for the same account from passing the precheck at the same moment. The per thread worker only serialises one thread, and a user can have two threads.
**Why it matters**: Spec 0012 lists "at most one pending `mfa_clear` approval per account" as a key invariant. Two cards for one person would appear in the IT channel. Approving the second one after the first has cleared the methods ends `failed` with "nothing to clear" and an escalation, which is noise IT has to read.
**Suggested fix**: Add a partial unique index on `approvals (requester_account, tool_name) WHERE status = 'pending'` in a new migration, and treat the unique violation in `Defer` as the `already_pending` or reuse path. Or soften the invariant wording in the spec to "usually".

### 🟡 A click after the tick has expired the approval gets the wrong text, `internal/audit/approvals.go:312`
**Problem**: `refusalReason` returns `already decided` for every status other than `pending`, so a row the tick already moved to `expired` answers with `approval_decided` ("This request was already decided."). `expired` is only returned while the row is still `pending` past `expires_at`.
**Why it matters**: AC-9 and AC-18 say a click after `expires_at` gets `approval_expired`. The tick runs every 30 seconds, so most late clicks land after the row has moved and see the wrong text. `TestLateClickIsRefusedExpired` only covers the short window before the tick.
**Suggested fix**: Return `expired` when `a.Status == "expired"`, and add a test that clicks on an expired row.

### 🟡 The user is told "Your ticket is closed" even when it was not, `internal/agent/replies.go:149`
**Problem**: `TextMFACleared` always ends with "Your ticket is closed." The card correctly says "Ticket left open." when `ticket_closed` is false, and `TestMFAOutcomeTicketLeftOpen` asserts the user still gets `TextMFACleared` and the conversation goes to `resolved`.
**Why it matters**: The user and the card disagree, and nothing tells IT that a resolved conversation has an open ticket (closed or merged by hand is fine, a failed close is not).
**Suggested fix**: Pick a second fixed text for the left open case (spec amendment), or drop the last sentence from the shared text. Consider a note or tag on the ticket when the close failed.

### 🟡 Graph failures log `cause` "other", `internal/tools/refusal.go:212`
**Problem**: `cause()` knows LDAP, Zammad and network errors but not `*graph.Error`. `graphFailure` wraps Graph errors in the `unavailable` failure, and `tool_call_failed` then logs `cause=other`.
**Why it matters**: The live probe already found a 400 on `signInPreferences` and the feature depends on admin consent for a granular permission. A 403 from a missing consent would be indistinguishable from a timeout in the logs. The cause token is fixed and safe, so adding `graph_<status>` leaks nothing.
**Suggested fix**: Add a `graph_<status>` branch using `graph.Status(err)`, and extend `internal/cause` and its test the same way.

### 🟡 Live probe issues a Temporary Access Pass if the permission is ever wider, `internal/graph/live_test.go:75`
**Problem**: The probe POSTs `temporaryAccessPassMethods` to prove a 403. If the app were ever given the fallback `UserAuthenticationMethod.ReadWrite.All` (which AC-20 allows), the call would succeed and mint a real one time sign in code for the demo user. The test then only reports an error.
**Why it matters**: A test that is meant to prove "cannot" would create the credential it checks for. It is gated by `TEST_ENTRA`, so exposure is small.
**Suggested fix**: If the POST returns 2xx, delete the pass it created (or fail with a loud message naming the user), and say so in the test comment.

### 🟡 Clear order with several Authenticator registrations is unverified, `internal/tools/mfa_clear.go:272`
**Problem**: `clearOrder` deletes phones first and Authenticators last, in list order. Graph refuses to delete the user's default method while others remain. With two Authenticator registrations, whichever is the default may come first and fail. The probe in journal 0041 only covered one Authenticator plus phones.
**Why it matters**: The spec allows `Authenticator app (n)` with n above 1. A failure here is safe (stops, escalates, "check by hand") but it makes a normal case look like a failure.
**Suggested fix**: Either confirm against Graph with two registrations and note the result, or on a refused Authenticator delete try the remaining Authenticators before giving up. Add a fake Graph test for two registrations.

### 🟡 List route does one query per row and the tick re reads the same rows, `internal/approvalapi/approvalapi.go:201`
**Problem**: `GET /approvals` builds `ExecutionOf` for every executed or failed row (up to 100 queries), and `adopt` (`internal/agent/tick.go:93`) calls it every 30 seconds only to read ids and thread columns, then tries up to 100 `AdoptApprovalCard` inserts.
**Why it matters**: Cheap at Noord's volume, but the cost scales with approvals in the window, and the follow up for #15 widens that window.
**Suggested fix**: Give the list route a light form without `execution`, or add a `has_card` style filter; for adopt, skip approvals that already have a card.

### 🟡 No test for the execute timeout firing mid clear or for the duplicate pending race, `internal/tools/mfa_clear_test.go`
**Problem**: `ExecuteTimeout` is set in the harnesses but nothing makes Graph hang past it. `TestApproveFinishesWhenTheClientLeaves` covers the client leaving, not the deadline. There is also no concurrent test for two requests on one account.
**Why it matters**: The timeout path is where a half finished clear and `approval_mark_lost` meet; the first finding above is also untested.
**Suggested fix**: Add a fake Graph delete that blocks until the context ends and assert outcome `error`, `failed` status and the right counts. Add a two goroutine request test once the index exists.

### 🟡 CI fork check fails open when the head repository is gone, `.github/workflows/ci.yml:26`
**Problem**: `github.event.pull_request.head.repo.fork` is null when the fork was deleted, so the expression picks `rpi01` and outside code runs on the Pi. This predates the feature work but is on the branch.
**Why it matters**: The runbook promises outside code never reaches the Pi.
**Suggested fix**: Flip the test so the Pi is used only when `head.repo.full_name == github.repository`, and otherwise `ubuntu-latest`. Also check that runner groups require approval for outside contributors.

## Strengths
- The approval state machine is in SQL and the audit pair for every move is written in the same transaction: `ApproveApproval` and `DenyApproval` carry the approver, expiry and self checks, refused clicks are audited as `denied_policy` with the reason, and the Postgres race test shows exactly one winner.
- `Execute` re reads the row before running (the journal 0039 fix), re checks the approver, runs detached from the HTTP request under its own timeout, reads the kill switch twice and re checks the account and the Entra user before any delete, stops at the first failed delete, and never retries. `Abandon` turns a stuck `approved` row into `failed` instead of ever re running it.
- The design closes the lost result gap: the card row is written in the same transaction as the stored tool result, and the tick adopts approvals the agent never saw (with the journal 0043 timeout setting fixed by one shared `ApprovalWindow`).
- Settling is careful: it escalates first, then settles once with a guarded UPDATE, runs on the thread's own worker, and uses the approval's own timeout for the give up limit.
- Credential and PII hygiene held: the new routes are not MCP tools (`TestApprovalRoutesAreNotTools`), `approvalapi` is on both deny lists, phone numbers and device names never leave the tool server, `approval_id` is the only new log key, and a canary test covers the whole flow. No real names, emails, ids or secrets in the diff or the new docs.
- Graph default method ordering (journal 0041) is handled with a fixed fallback order and tests, and the card and ticket notes show method counts only.
